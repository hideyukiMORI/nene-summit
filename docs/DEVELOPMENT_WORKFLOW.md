# 開発手順

1. 現在地と依頼範囲を確認し、焦点を一つにした Issue を選ぶ。初期化だけは Issue 不要。
2. 要件、影響する規則 ID、正典経路、該当 ADR と waiver を読む。
3. 最新 main から [COMMIT_CONVENTIONS](COMMIT_CONVENTIONS.md) の形で作業ブランチを作る。
4. 設計・境界・保存形式・対応環境・ゲートを変える場合は ADR を先に書く。
5. 最小の実装と必要な振る舞い検証を追加し、狭い検査で進める。
6. Draft PR に目的・規則・検証・残る課題を書く。
7. 最終変更に対して make check を実行し、CI も確認して Ready にする。コミットメッセージはフックと同じ検証器が範囲内を見る。
8. マージする依頼がある場合は squash。current と正本文書を更新する。

ゲートが落ちたら原因を直す。期待値・seed 件数・閾値を下げて成功させない。
規約変更には根拠と移行が必要。抑制は [waiver](waivers/README.md) に期限付きで記録する。

規範は docs、判断理由は ADR、一時例外は waiver、作業状態は Issue / PR と current。
チャットだけに長期的な決定を残さない。兄弟で認められた自動操作の権限は引き継がない。
具体的な依頼があれば、その範囲の実装・検証を進める。細かな設計選択ごとに停止せず記録して進める。
製品要件の大きな追加・確定要件の削除・公開 Release は、その時点の依頼を確認する。

初期ドキュメント CI は製品を検証しない。現在の実体は [QUALITY_GATES](QUALITY_GATES.md) を参照。
